# Plan Templates（计划模板）

这些模板用于帮助选择最适合当前任务的 Plan（计划）结构。

它们不是必须机械填写的表格。

下面给出一套**推荐骨架**作为参考，但具体章节由当前任务决定——agent 应按任务的工程风险自由增减章节、调整顺序、改写章节名。只要最终结构能让审阅者一眼看清「要做什么、依据是什么、怎么执行、如何验证」即可。

---

# 推荐骨架（参考）

```markdown
# 计划：[任务标题]

## 一、目标
一句话说明本次计划要做什么。

---

## 二、背景
- 当前环境：
- 当前状态：
- 用户需求：
- 已知事实：

---

## 三、执行步骤
1. ...
2. ...
3. ...

---

## 四、约束与保证
1. ...
2. ...
3. ...

---

## 五、风险与回退

### 风险
- ...

### 回退
- ...

---

## 六、范围外事项
1. ...
2. ...
3. ...
```

## 按任务调整章节

骨架只是参考，不是固定表格。下面列出常见调整方向，agent 应按当前任务自行判断采用哪些。

### 在「执行步骤」之前加「设计」章节

涉及方案选择、架构讨论、接口设计时，在「二、背景」和「三、执行步骤」之间加：

```markdown
## 三、设计
（或：方案 / 架构 / 接口设计）
说明最终采用的机制、关键边界、主要流程。
```

后续章节顺延编号（「四、执行步骤」「五、约束与保证」...）。

### 在「背景」内补子节

- Feature：`### 用户流程` / `### 状态 / 数据流`
- Bugfix：`### 问题现象` / `### 预期行为` / `### 根因`（根因未确认时不要写最终修复计划，继续调查）
- Architecture：`### 设计约束` / `### 当前架构`
- Migration：`### 当前状态` / `### 目标状态`

### 在「约束与保证」内补子节

- Feature：`### 验收标准`
- Refactor：`### 行为不变量`（列出必须保持不变的行为）
- Integration：`### Failure Handling` / `### Compatibility`
- Migration：`### 迁移期间兼容性` / `### 数据 / 状态转换`

### 在「执行步骤」内补子节

- Architecture：`### 状态机` / `### 控制流 / 数据流` / `### 职责边界` / `### 关键决策` / `### 失败 / 边界行为`
- Migration：按 `### Phase 1` / `### Phase 2` 划分
- Refactor：`### 迁移策略`

### 在「风险与回退」内补子节

- Bugfix：`### 回归风险`
- Migration：`### 回滚`（仅当回滚真的可行且有意义时才写）

### 简化小任务

Small Change 不需要把所有章节都写满：「背景」「约束与保证」「风险与回退」「范围外事项」可以只写一行或留空，但保留章节标题让审阅者一眼看到完整性。

简单任务写短计划是优点，不是缺点。不要为了"看起来完整"把小改动写成大型设计文档。

# 排版规则

## 章节编号

推荐使用「一、二、三、...」中文数字编号，保持计划之间风格一致。

章节顺序按任务逻辑组织，常见顺序：

> 目标 → 背景 → （设计） → 执行步骤 → 约束与保证 → 风险与回退 → 范围外事项

「设计」是否单独成章由任务复杂度决定；简单任务可以省略。

只在 `##` 章节内追加 `###` 子节，不要新增顶层 `##` 章节让结构超过三层。

## 标题

只使用：

- `#`：仅用于计划标题（`# 计划：[任务标题]`）
- `##`：主要章节
- `###`：章节内补充小节

不要制造过深标题层级。

## 分隔线（`---`）

骨架每个 `##` 章节之间**必须**各加一条 `---`，让审阅者一眼看到阶段切换。

`###` 子节之间**不要**再加 `---`——否则满屏水平线反而凌乱。

文件末尾不需要 `---`。

## 段落

保持短小。

一个段落尽量只表达一个主要意思。

## 表格

适合用于：

- 横向比较；
- Ownership（职责归属）；
- 状态矩阵；
- 已确认决策；
- Compatibility Matrix（兼容性矩阵）。

普通说明不要强行塞表格。

## 流程图

适合用于：

- 状态机；
- 执行流；
- 数据流；
- 生命周期。

一句话能讲清楚时不要画图。

## 路径与符号

以下内容使用反引号：

- 文件路径；
- 函数名；
- 类型名；
- 工具名；
- 状态名；
- 命令；
- 配置项。

## 强调

粗体应少量使用。

不要把每个"重要名词"都加粗。

## 讨论历史

最终 Plan（计划）不是聊天记录。

应删除：

- 已经淘汰的方案；
- 重复推理；
- 多轮来回聊天内容；
- 不影响最终实现的争论。

只有当"为什么拒绝某方案"能够防止执行阶段再次踩坑时，才保留必要说明。

## 未确认项

不要把未解决问题隐藏在确定语气里。

可以使用：

```markdown
> **待确认：** ...
```

但真正 Approval-Ready（可审批）的计划通常不应该还有会阻塞执行的重要待确认项。
