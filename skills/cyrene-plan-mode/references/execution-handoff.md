# Execution Handoff（执行交接）

Approved Plan（已批准计划）是 Plan Mode（计划模式）与执行阶段之间的桥梁。

目标：

> 保留用户已经 Review（审阅）并批准的关键决定，同时不给执行阶段套上一份僵硬脚本。

---

## 1. “批准”意味着什么

用户批准 Plan（计划）意味着：

- 目标已经认可；
- 主要设计方向已经认可；
- 范围已经认可；
- 可以开始真正实施。

但不意味着：

> 每一个低层实现细节都已经不可修改。

执行阶段仍可能发现规划阶段没有必要、也无法提前确认的现实细节。

---

## 2. 真实代码优先于计划假设

执行阶段遵循：

> **Workspace Ground Truth（工作区事实） > Plan Assumption（计划假设）**

如果当前代码与计划中的某个假设不同，不要为了“严格按照计划”而强迫代码符合假设。

先判断差异属于哪一种。

### Implementation Detail（实现细节）

例如：

- Helper Function（辅助函数）实际名称不同；
- 项目已有更合适的局部实现方式；
- 行号已经变化；
- 测试实际位于另一个文件。

这种情况可以正常调整。

必要时同步修改 Todo（待办事项）。

### Material Design Conflict（重大设计冲突）

例如：

- 已批准架构与真实生命周期无法兼容；
- 按计划实现会违反用户明确约束；
- 计划依赖的 API（接口）不存在；
- 实际实现必须显著扩大 Scope（范围）；
- 安全或 Compatibility（兼容性）语义必须改变。

这种情况不要偷偷重新设计。

应把冲突告诉用户，并在必要时重新获得决定。

---

## 3. 从 Plan（计划）生成 Todo（待办事项）

执行开始时，根据已批准 Plan（计划）生成一份简洁 Todo（待办事项）。

Todo（待办事项）是执行阶段的工作笔记，不是 Plan（计划）的第二份全文副本。

推荐：

```text
[ ] 增加会话级 Plan 状态
[ ] 接入 Plan Mode 工具可见性
[ ] 实现用户审批转换
[ ] 接入计划 Review 卡片
[ ] 增加状态与权限验证
```

不要写：

```text
[ ] 完成整个计划
```

也不要写成：

```text
[ ] 打开文件
[ ] 找到函数
[ ] 修改函数
[ ] 保存文件
```

Todo（待办事项）应跟踪有意义的执行进度。

---

## 4. Todo（待办事项）允许变化

Approved Plan（已批准计划）记录的是：

> 用户 Review（审阅）过的实现意图与主要设计。

Todo（待办事项）记录的是：

> 当前执行现实。

因此以下情况可以调整 Todo（待办事项）：

- 实际实现表明步骤顺序应该改变；
- 一个 Task（任务）需要拆开；
- 两个 Task（任务）应该合并；
- 发现新的验证步骤；
- 某个 Plan Assumption（计划假设）被真实代码否定。

不要因为 Todo（待办事项）是动态的，就偷偷改变用户已经批准的产品或架构决定。

---

## 5. 按有意义的实现单元执行

优先完成一个完整实现单元，再验证，然后进入下一项。

一个有意义的实现单元通常会产生可观察结果，例如：

- 某个 State Transition（状态转换）已经可用；
- 某工具只在正确 Mode（模式）下出现；
- 某 UI（用户界面）操作已经接到后端；
- 某 Bug（问题）已经可重复验证地修复；
- 某迁移阶段已经完成。

不要用“修改了几个文件”衡量真实进度。

---

## 6. Verification（验证）属于执行本身

代码写完不代表 Task（任务）已经完成。

在条件允许时，应完成计划中对应的 Verification（验证）后，再认为该 Task（任务）完成。

可能包括：

- Unit Test（单元测试）
- Integration Test（集成测试）
- Type Check（类型检查）
- Build（构建）
- Lint（静态检查）
- Targeted Runtime Check（针对性运行验证）
- UI Interaction（用户界面交互验证）
- State Transition Inspection（状态转换检查）
- Permission Denial Test（权限拒绝测试）

不得声称执行了没有真正执行的验证。

---

## 7. 保留用户已经批准的约束

执行过程中持续记住用户明确的约束，例如：

- 不增加新依赖；
- 不改变 Public API（公共接口）；
- 保留兼容性；
- 复用已有权限模型；
- 不再造第二套状态机；
- v1 只做内存状态。

实现方便不能自动覆盖已批准约束。

---

## 8. 不要重新争论已经结束的决定

已批准方案中已经确定的设计，不要因为“还有另一个也合理的方案”就重新打开讨论。

只有新的实现事实显著改变了原来的 Trade-off（取舍），才值得再次提出。

这样可以避免：

> 执行阶段又退回无限架构讨论。

---

## 9. 完成判断

认为执行完成之前，应重新对照：

- 用户批准的目标；
- Plan（计划）中的主要实施任务；
- Verification（验证）标准；
- 用户明确约束。

不要仅根据：

> “Todo（待办事项）全部打勾了”

判断任务完成。

真正完成意味着：

> **用户批准的行为已经存在，并且相关验证能够支持这一结论。**
