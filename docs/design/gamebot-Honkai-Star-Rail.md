## 0. 一句话目标

让 Cyrene 通过一组**屏幕自动化 Tools** + 一份**游戏知识 Skill**，用自然语言驱动"清体力 / 每日实训 / 领奖励"等游戏任务：

**本地工具做手脚（快、稳、省），Harness 模型做大脑（看图决策、灵活兜底）。**

---

## 1. 背景与核心决策

### 1.1 调研结论（March7thAssistant，2026-08-29 完成）

对 March7thAssistant 的完整源码走读结论（三层结构）：

| 层 | 它的做法 | 评价 |
|---|---|---|
| 任务编排 | 固定顺序 + 配置开关 + "上次完成时间戳 vs 凌晨4点刷新"闸门 | 闸门设计好，调度逻辑死板 |
| 具体任务 | 每任务一个手写脚本：截图 → 模板匹配/OCR 找元素 → 点击 → 重试 | 稳定但极脆，游戏 UI 一改就大面积失效 |
| 自动化引擎 | 统一 `find_element(target, find_type, crop, max_retries)` 入口 + 输入抽象（本地/云游戏/内存注入三种"手"） | **可借鉴的抽象，接口设计干净** |

两个关键洞察：

1. **它的脆弱性来自"模板匹配死绑 UI 版本"**——每次游戏更新都要志愿者重截模板图，维护成本远大于开发成本。
2. **它需要一个几十个开关的 GUI 面板，因为它没有大脑**——所有"刷什么、几点跑、用不用燃料"的决策都要用户提前用表单填死。

### 1.2 核心决策：Tool + Skill，不做配置面板式 UI

| March7thAssistant 用 GUI 解决的问题 | Cyrene 的对应物 |
|---|---|
| 配置面板选副本/次数/开关 | 用户对 agent 说"帮我清体力，刷金花萼"（自然语言即配置） |
| 定时任务表单 | 对话约定 + 后续调度能力（P2） |
| 日志窗口 | Harness 工具调用过程天然可见 |

**理由**：Cyrene 本身就是 agent harness（见 `2026-08-08-cyreneHarnessloopdesign.md`），核心哲学"模型自由决策，Runtime 兜底"。给 agent 套一个表单面板等于退化成死程序。配置面板是给没有大脑的工具用的。

### 1.3 混合执行哲学（与 Harness 哲学同构）

| 车道 | 执行者 | 速度 | 成本 | 用途 |
|---|---|---|---|---|
| **快车道** | 本地工具（模板匹配 + OCR） | 毫秒级 | 零 | 高频、位置固定的操作（点"再来一次"、认按钮） |
| **慢车道** | Harness 模型看截图决策 | 秒级（1~5s/步） | 按 token 计费 | 计划、识别新 UI、异常诊断、无模板的冷门操作 |

**关键点：慢车道不引入任何额外视觉 API。** Harness 驱动模型本身就是多模态的——工具返回截图图像块，模型看图决定下一步，这本来就是 Harness 的工作方式。Skill 文件即 prompt。

## 3. 架构设计

### 3.1 三层结构

```
┌─────────────────────────────────────────────────────┐
│ Skill 知识层  skills/game-hsr/SKILL.md               │
│ 流程知识 + 界面名 + 禁区黑名单 + 护栏规则 + 收工条件   │
│ → 教 agent "怎么做"，纯文字，不写代码                 │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│ Tools 能力层  screen-tools.ts（ToolDefinition[]）     │
│ 会话管理 / 无头截屏 / 本地找元素 / 键鼠注入 / 等待    │
│ → 快车道，重试/裁剪/超时内置于工具                    │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│ 模型兜底层 = Harness 本体（无新增模块）                │
│ find 失败 → 工具返回"未找到 + 标注截图（set-of-mark）" │
│ → 模型看图决定下一步动作 → 再调工具执行                │
└─────────────────────────────────────────────────────┘
```

### 3.2 会话模型

自动化不是单次工具调用，而是一段**受控会话**：

- `automation_session_start` 打开会话：校验游戏窗口存在、校验权限总闸、开始记录动作日志、启用急停热键。
- 会话内的屏幕工具只在**活动会话**下可用（未开会话时 `screen_click` 等直接拒绝执行）。
- `automation_session_stop` 或急停热键或会话超时 → 立即停止输入注入，释放钩子。

**审批语义（session-scoped capability）**：`automation_session_start` 的用户批准建立一份**会话级能力授权**；活动会话内 `screen_click` / `screen_key` / `screen_scroll` 仍按 `dangerous` 记录与审计，但**不再逐次请求用户审批**。会话停止、超时或急停后授权立即撤销，下次会话重新批准。否则"允许点击？允许按键？允许点击？"的逐次审批会让自动化彻底不可用。

**理由**：键鼠注入是全项目风险最高的能力，必须有一个显式的、可快速撤销的"持枪许可"边界，而不是散装工具随时可打。会话授权解决的是**"Cyrene 有没有权进行输入"**；每次注入前的逐次前台校验（§3.4 / §6）解决的是**"这次输入现在应该打到谁身上"**——两道独立的闸，不可互相替代。

### 3.3 快/慢车道切换规则（写入 skill 与工具返回值约定）

- 工具带模板/文本查找，命中 → 快车道直接返回坐标，模型只管下一步动作。
- 未命中 → 工具返回 `not_found` + 当前截图（可选 set-of-mark 标注）→ 模型看图决策（慢车道）。
- 模型若发现"这是新按钮但会反复出现"，可调 `screen_template_save` 把当前区域存为模板（P1 自学习，见 §7）→ 下次走快车道。**越用越快，越用越省。**

### 3.4 观察-动作绑定契约（frame contract）

**问题**：归一化坐标只解决分辨率漂移，不解决**过期观察（stale observation）**——模型看的是 frame A，思考几秒后画面已是 frame B，按 A 的坐标点击就会点错地方。这是屏幕 Agent 最高频的错误模式，必须在架构层封死，而不是靠 prompt 提醒。

**契约**：

- `screen_capture` 返回**观察帧**对象：`{ frameId, hwnd, pid, clientRect, capturedAt, image }`；
- 一切注入类工具（`screen_click` / `screen_key` / `screen_scroll`）**必须携带 `frameId`**，不接受裸坐标调用；
- Runtime 在**每一次注入前**执行校验清单（毫秒级本地代码）：

| 校验项 | 失败错误码 |
|---|---|
| 会话仍有效 | `session_invalid` |
| 目标 HWND/PID 与帧登记一致（游戏未重启/未换窗口） | `target_changed` |
| 目标窗口仍是前台窗口 | `target_not_foreground` |
| 帧未超过允许过期时间（P0 定 2s，实测调整） | `stale_frame` |
| 窗口尺寸/位置与帧的 clientRect 一致（未移动/未缩放） | `target_moved` |

- 任一校验失败 → 注入**拒绝执行**，返回结构化错误码并提示模型重新 `screen_capture`，绝不"猜着点"。

**理由**：`screen_click(x, y)` 一旦先施工、后改成 `screen_click(frameId, x, y)`，会牵连 skill、工具表、日志、测试与会话管理器全线返工——**输入契约必须在设计稿冻结**。

## 4. 工具清单

| 工具 id | 作用 | risk | 备注 |
|---|---|---|---|
| `automation_session_start` | 开启自动化会话（权限校验、急停启用） | dangerous | 返回会话 id；批准即建立会话级授权（§3.2），需用户确认链路 |
| `automation_session_stop` | 结束会话，立即停止注入 | safe | 急停热键等价于此 |
| `automation_session_status` | 查询会话状态/已执行动作数 | safe（0 配额） | 供模型自检动作预算 |
| `screen_capture` | 无头截屏（窗口/归一化区域裁剪） | safe | 返回观察帧 `{frameId, hwnd, pid, clientRect, capturedAt, image}`（§3.4）；**不弹 overlay** |
| `automation_wait` | 傻等固定时长（100ms~30s） | safe | **P0 必备**——`screen_wait_for` 依赖 P1 的模板/OCR，P0 等"战斗结束"这类无信号场景只能靠它，避免模型连拍空转 |
| `screen_find_image` | 模板匹配找元素，支持 crop + 阈值 + 内置重试 | safe | P1；命中返回坐标框，未命中返回截图 |
| `screen_find_text` | OCR 找文字（含"最近锚点"模式：在锚点方位找最近的文字） | safe | P1；对应 March7thAssistant 的 min_distance_text 思路 |
| `screen_click` | 点击观察帧内坐标（`frameId` + 归一化 x/y） | dangerous | 注入前逐次校验 §3.4 清单，失败返回结构化错误码 |
| `screen_key` | 按键/组合键（绑定 `frameId`） | dangerous | 同上 |
| `screen_scroll` | 滚轮（绑定 `frameId`） | dangerous | 同上 |
| `screen_wait_for` | 条件等待：模板/文字出现，带超时 | safe | P1（依赖 find 能力）；上线后 `automation_wait` 的"傻等"升级为"条件等待" |
| `screen_template_save`（P1） | 把截图区域存为模板，供 find_image 复用 | safe | 模板自学习 |

约定：

- 所有坐标采用**归一化比例**（0~1）存取，运行时按实际窗口尺寸换算（借鉴 March7thAssistant，防分辨率漂移）。
- **一切注入类输入必须绑定观察帧**：`screen_click` / `screen_key` / `screen_scroll` 的 inputSchema 必填 `frameId`，Runtime 按 §3.4 清单逐次校验后执行。
- `screen_find_*` 的 `max_retries`/`retry_delay` 内置于工具，业务层（skill）不写重试循环。
- 所有 dangerous 工具执行前检查会话授权（§3.2）+ 动作预算余量（§6）。

## 5. Skill 设计

新增 `skills/game-hsr/SKILL.md`（frontmatter: `modes` 限定、`hiddenFromUi: false`）。内容构成（全部自然语言，不含代码）：

1. **流程知识**（借鉴 March7thAssistant 的编排逻辑，用文字重述）：
   - 清体力：读体力 → 算轮次 → 选副本 → 传送 → 设连刷次数 → 开打 → 等"再来一次" → 退出；
   - 每日实训补缺口：读清单 → 利用大任务顺路完成小任务（先清体力再补缺口）→ 积分够 500 提前收工；
   - 领奖励：找红色感叹号 → 按类型进对应界面逐个领取。
2. **禁区黑名单**：充值、购买、设置、账号、客服、任何涉及真实货币/账号安全的按钮——模型永不点击。
3. **护栏规则**：单任务动作预算（默认 60 步）；连续 N 次找不到目标即上报而非硬猜；"不确定就问用户，不猜"。
4. **收工与报告**：完成后向用户汇报做了什么、消耗多少步、有没有异常。
5. **已知坑**：云游戏超时弹窗、遗器背包满提示、切换角色视角确认框等异常分支的处置约定。

## 6. 安全与护栏（P0 不可裁剪）

| 风险 | 护栏 |
|---|---|
| agent 动真实键鼠（全局最高风险） | 工具组 `risk: dangerous` + 设置里"允许控制键鼠"总闸**默认关** + 首次使用确认链路（建立会话级授权，§3.2）+ 仅限活动会话内执行 |
| 输入打进别的程序（Alt+Tab / Win 键 / 弹窗 / UAC 抢焦点） | **Runtime 不变量：每一次输入注入前必须重新验证目标窗口仍是前台窗口**（§3.4 清单），失败拒绝注入并返回 `target_not_foreground`。会话开始时校验一次远远不够——用户随时可能切走窗口 |
| 失控/死循环 | 会话级动作预算（超预算自动停止并报告）+ 会话超时 + 工具内置重试上限 |
| 用户失去掌控感 | **全局急停热键**（如 F12，原生层直接断注入，不经过模型）+ 运行状态浮窗（P1：缩略截图 + 当前步 + 暂停/停止） |
| 误触敏感按钮 | **P0**：skill 语义黑名单（模型侧，软约束）+ 工具层**目标进程限制**（只允许向会话登记的游戏 PID 注入）+ 前台窗口限制（§3.4）+ 会话/急停/预算兜底。**P1**：OCR/模板能力落地后，工具层加敏感元素二次识别（对点击目标处做黑名单词/图标匹配，命中直接拒绝并上报）——此时才构成真正的"双重拦截" |
| 提权不对称 | 游戏以管理员运行而 Cyrene 未提权时，注入会静默失效——工具必须**显式检测并报错**，禁止静默降级 |
| 游戏反作弊/封号 | 文档明确免责：自动化游戏操作违反多数游戏用户协议，风险用户自担；默认仅支持国服 PvE 日常场景 |
| 截图隐私 | 会话截图落盘位置固定并随会话结束清理（可配置保留），不进聊天历史之外的地方 |

## 7. 分期计划（意图，非施工表）

### P0 —— 验证"模型当大脑"是否成立（最小闭环）

- 无头截屏工具（`screen_capture`，返回观察帧）；
- 输入注入原生模块（SendInput）+ `screen_click` / `screen_key` / `screen_scroll`（绑定 `frameId` + 逐次校验，§3.4）；
- `automation_wait`（P0 唯一等待能力；`screen_wait_for` 属 P1）；
- 会话管理三件套 + 全局急停热键 + 会话级授权（§3.2）；
- `game-hsr` skill v1（只写清体力流程）；
- ~~前置：多模态发图已知问题修复~~（已解除，见 §8.1）。

P0 成功标准（四维，缺一不算过）：

**功能**
- 用户一句"帮我清体力"，agent 可完整完成一次任务；
- 模型可通过 截图 → 决策 → 动作 → 再截图 形成稳定闭环。

**安全**
- 急停热键在任意步骤立即终止输入；
- 用户 Alt+Tab 后，后续注入必须被拒（`target_not_foreground`）；
- 会话超时 / 动作预算耗尽后自动停止；
- 目标窗口退出或重启后，不得继续向旧目标注入（`target_changed`）。

**正确性**
- 输入动作必须绑定有效观察帧，§3.4 校验清单全部落地；
- 工具执行成功 ≠ 任务成功——任务状态必须经后续视觉观察确认（模型复看截图）。

**性能（基线采集，为 P1 提供对照）**
- 记录一次完整任务的：步数、模型调用次数、截图张数、总耗时、上下文占用。

P0 跑完要能回答的是"**这条路线值得继续加 OCR 和模板缓存吗**"，而不只是"成功刷了一次本"。

### P1 —— 提速省钱

- `screen_find_image` / `screen_find_text`（本地快车道）；
- `screen_template_save` 模板自学习（答过的问题不再问模型）；
- 每日实训 / 领奖励 skill 扩展；
- 运行状态浮窗。

### P2 —— 面向日常使用

- 定时调度（对话约定"每天早上跑一次"）；
- 模板库沉淀与分享；

## 11. UI 设计（P0 极简 + P1 浮窗）

### 11.1 总原则

UI 只做**安全阀 + 可见性**，不做操作面板。旧 game-bot 子系统（2026-08-21 删除，commit `d15bacb`）的 UI 是设置表单，因为它靠 YAML 配方驱动、用户必须用表单配置"做什么"；新架构里这件事归对话（"帮我清体力，刷金花萼 6 次"），配置面板的活儿不存在了。

| 职责 | 形态 | 期 |
|---|---|---|
| 安全总闸 | 设置页一个开关 | P0 |
| 会话确认 | 复用现有 PermissionPanel ask 流程，零新 UI | P0 |
| 运行可见性 + 急停反馈 | 运行状态浮窗 | P1 |

### 11.2 P0 的 UI（极简）

1. 设置总闸："允许控制键鼠（GameBot）"一个开关，默认关，挂现有设置窗口（旧 gamebot panel 曾挂载于此，模式现成，但只做一行开关）；
2. 会话确认：`automation_session_start` 走既有 ask 流程，批准即建会话（§3.2）；
3. 急停反馈：F12 触发后托盘/主窗口一条"自动化已急停"提示。

P0 不做浮窗——它是体验优化，P0 验证失败即为白做。

### 11.3 P1 运行状态浮窗

**核心矛盾**：游戏全屏时用户看不见主窗口，但需要知道 agent 在干嘛、能否叫停。

```
┌─ 屏幕右上角 ─────────────────┐
│ ┌──────────────────────────┐ │
│ │   [最近一帧截图缩略图]     │  ← 复用 frame-registry 已拍帧，零额外截屏
│ └──────────────────────────┘ │
│ 正在执行: 等待战斗结束         │  ← session-manager 事件流
│ 步数 12/60 · 已运行 4 分 12 秒 │  ← 预算余量，超 80% 变警示色
│  [ 暂停 ]      [ ⏹ 停止 ]    │  ← 停止 = automation_session_stop
│  急停热键: F12                │
└──────────────────────────────┘
```

**技术约束**：

| 点 | 做法 |
|---|---|
| 窗口形态 | 无边框、`alwaysOnTop`、**`focusable: false`**、`skipTaskbar` 的小 BrowserWindow——绝不抢游戏焦点（抢焦点即触发 `target_not_foreground`，自动化自己杀死自己，这是浮窗第一铁律） |
| 挂载 | `WindowManager` 下新增浮窗类型 |
| 数据流 | session-manager 发事件（开始/步数/预算/终止）→ IPC 推浮窗，照 `WorkStreamEventBridge` / `cyrene.todo` 事件桥模式 |
| 暂停语义 | 会话保持、停止注入、模型收到"已暂停"挂起；恢复后继续预算计数 |
| 全屏遮挡 | 独占全屏下浮窗被盖住——接受，F12 热键仍可达（急停不能只有按钮） |

**主窗口**：composer footer 加一个状态 chip（做法与位置参照 `ContextUsageRing`）——"🎮 运行中 · 12/60"，点击唤起浮窗；无活动会话不渲染。

### 11.4 明确不做的 UI

- ❌ 副本/次数/定时配置表单——对话解决（§1.2 核心决策）
- ❌ 模板管理界面——`screen_template_save` 自动落盘
- ❌ 任务调度面板——P2 对话约定，需要时再加极简列表
- ❌ 独立游戏任务页——GameBot 不配 tab
